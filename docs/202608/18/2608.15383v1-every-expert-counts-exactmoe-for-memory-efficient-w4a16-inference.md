## 摘要
稀疏混合专家（MoE）语言模型通过仅激活每个词元的一小部分专家来减少算术运算，但部署时仍需要存储和移动完整的专家库。我们提出了ExactMoE，一种推理设计，仅对路由专家应用对称的组大小为128的4比特权重量化，以内核原生的MARLIN形式将这些专家存储在固定主机内存中，并通过可配置的GPU驻留槽位缓存和融合分组MoE内核执行所有选中的专家。路由器、注意力、嵌入、归一化层和语言模型头保持BF16精度。“Exact”指的是完整的专家可用性和未改变的top-k路由过程：没有专家被剪枝、替换或强制在CPU上执行。这并不意味着与BF16模型在数值上完全一致。在单个NVIDIA L4上评估的OLMoE-1B-7B-0924-Instruct中，16槽位配置将峰值保留GPU内存从14.168减少到1.836 GiB（减少87.04%），同时保留了BF16解码吞吐量的81.85%。完全驻留的64槽位配置达到31.923 token/s，而BF16为21.662 token/s，同时保留4.061 GiB内存。在12,450个零样本多项选择题中，ExactMoE获得70.3534%的归一化准确率，而BF16为70.8996%，保留了基线准确率的99.23%。在匹配的16词元消融实验中，融合分组执行比顺序W4参考快1.97倍。这些结果确定了完整专家MoE推理的一个实用内存-传输吞吐量边界。

## Abstract
Sparse mixture-of-experts (MoE) language models reduce arithmetic by activating only a small subset of experts per token, yet deployment still requires storing and moving the full expert bank. We present ExactMoE, an inference design that applies symmetric group-128 four-bit weight quantization only to routed experts, stores those experts in kernel-native MARLIN form in pinned host memory, and executes all selected experts through a configurable GPU-resident slot cache and fused grouped MoE kernels. The router, attention, embeddings, normalization layers, and language-model head remain in BF16. "Exact" refers to complete expert availability and an unchanged top-k routing procedure: no expert is pruned, substituted, or forced to execute on the CPU. It does not imply numerical identity with the BF16 model. On OLMoE-1B-7B-0924-Instruct, evaluated on a single NVIDIA L4, a 16-slot configuration reduces peak reserved GPU memory from 14.168 to 1.836 GiB (87.04%) while retaining 81.85% of BF16 decode throughput. A fully resident 64-slot configuration reaches 31.923 tokens/s versus 21.662 tokens/s for BF16 while reserving 4.061 GiB. Across 12,450 zero-shot multiple-choice questions, ExactMoE obtains 70.3534% normalized accuracy versus 70.8996% for BF16, retaining 99.23% of the baseline accuracy. In a matched 16-token ablation, fused grouped execution is 1.97x as fast as a sequential W4 reference. These results identify a practical memory-transfer-throughput frontier for complete-expert MoE inference.

# 《Every Expert Counts: ExactMoE for Memory-Efficient W4A16 Inference》论文总结

## 一、核心问题与研究动机

- **核心问题**：稀疏混合专家（MoE）语言模型虽然每个 token 仅激活少量专家，但部署时仍须将**完整专家库（expert bank）** 存储并搬运到 GPU 上，带来巨大的显存与主机-设备带宽开销。
- **背景权衡**：现有方案面临三难——要么将大专家库常驻 GPU（显存瓶颈）、要么从慢速内存层搬运专家（传输瓶颈）、要么压缩专家表示（量化误差）。已有工作分别从专家单独量化、混合精度、卸载/缓存系统、W4A16 高性能内核（MARLIN）等角度切入，但缺少一个**同时解决三个问题且不牺牲完整专家可用性**的统一系统方案。
- **研究问题**：能否将专家单独量化、内核原生存储、GPU 缓存与融合分组执行整合到一个运行时中，既保留模型的**全部专家**（不剪枝、不替换、不上 CPU），又避免逐专家执行和临时 FP16 物化？

## 二、方法论：ExactMoE

### 核心思想

只对**被路由的专家**（routed experts）施加对称 group-128 4-bit 量化和 MARLIN 内核原生打包格式；主机内存与 GPU 缓存共享**同一份内核原生表示**；推理时按波次（wave）用**融合分组 MoE 内核**执行所有被选中的专家。路由器、注意力、嵌入、归一化与 LM head 全部保留 BF16。

### 关键技术细节

1. **逐专家对称 W4 量化**：对每个专家矩阵，按输入维度分成长度为 128 的组，每组计算比例因子 `s = max|x| / 7`，将权重四舍五入并裁剪到 [-8, 7] 的 INT4 范围，构成数学参考 `Ŵ = s * q`。零组特殊处理。gate/up 投影按融合内核所需顺序拼接打包，down 投影单独打包。
2. **内核原生存储**：量化与打包在离线完成一次后，同一份 MARLIN 格式（含 packed qweights 和 FP16 scales）同时存放于**固定内存（pinned host memory）** 和 **GPU 缓存槽位**。缓存未命中时直接异步复制最终内核表示，**无需反量化或重打包**。
3. **可配置 GPU 槽位缓存**：每层拥有 C 个专家槽位（k ≤ C ≤ E），维护全局专家 ID 到槽位的映射及 LRU 时间戳。缓存未命中时替换当前波次未保护的 LRU 槽位，CUDA 事件防止槽位在计算尚未完成时被覆盖。C = E 时全量预载，禁用 ID 传输与替换逻辑。
4. **分组完整执行**：当活跃专家数超过 C 时，将活跃集合划分为多个波次（每个波次 ≤ C 个专家）。每个波次按以下流程执行：① 解析/加载波次内专家到槽位；② 构建全局 ID → 槽位映射（非活跃专家映射到哨兵）；③ 以完整 token 矩阵调用融合 MARLIN MoE 内核；④ 将波次输出累加到层结果；⑤ 记录完成事件后才允许复用槽位。每层仅两次分组 GEMM（一次融合 gate/up，一次 down），而非逐专家调用。路由器权重跨波次保留，不做波次内重新归一化。
5. **“Exact”的定义**：指**完整专家可用性** + **未修改的 top-k 路由过程**（路由器始终基于当前量化模型隐状态做决策，且所选专家全部参与计算）。它**不意味着**与 BF16 模型数值等价。

## 三、实验设计

### 模型与硬件

- **模型**：`allenai/OLMoE-1B-7B-0924-Instruct`（revision 7f1c97f…），16 个稀疏层 × 64 专家/层、top-8 路由、hidden size 2048、expert intermediate size 1024、路由专家参数约 6.44B。
- **硬件**：单张 **NVIDIA L4 GPU**（22.0 GiB 可用显存）+ 53 GiB 主机内存。
- **软件栈**：PyTorch 2.11.0+cu130、CUDA 13.0、Transformers 5.14.1、vLLM 0.26.0、MARLIN commit 1f25790。

### Benchmark 与对比

- **缓存容量扫描**：C ∈ {8, 16, 32, 64}，与 BF16 基线在同一 checkpoint、同一硬件上对照，指标包括 decode 吞吐、TTFT、峰值保留显存、缓存命中率、主机-设备传输量。
- **质量评估**：
  - **ARC-Easy**（570 题）、**PIQA**（1,838 题）、**HellaSwag**（10,042 题），共 **12,450 道配对零样本选择题**，报告归一化/原始准确率、Bootstrap 区间与 McNemar 检验；
  - 额外报告 WikiText-2（120 段落）与 Dolly-15k（120 样本）上的 teacher-forced 困惑度。
- **消融实验**：匹配 16 槽缓存状态下，**融合分组执行 vs. 逐专家顺序 W4 参考**的 16-token 对照，比较吞吐、贪婪 token 一致性与 logits 容差。
- **批量生成扫描**：batch ∈ {1, 2, 4, 8} 的单次扫描，考察批处理吞吐缩放，不涉及连续批处理调度器。
- **内核级验证**：gate/up 与 down 形状 × token 组规模 1–128 的内核正确性对照（对物化反量化 W4 参考）。

## 六、主要结论

- **内存-吞吐前沿**：16 槽配置将峰值保留显存从 14.168 降至 1.836 GiB（**−87.04%**），decode 吞吐保留 BF16 的 **81.85%**（17.73 vs 21.66 tok/s），代价是每请求 21.44 GiB 的专家搬运与 290 ms 的 TTFT；32 槽几乎追平 BF16 吞吐（21.69 vs 21.66 tok/s）且显存仍降 81.8%；64 槽全驻留达到 **31.92 tok/s（+47.4%）**，显存占用仅 4.06 GiB（−71.3%）。
- **质量保持**：12,450 题归一化准确率保留 **99.23%**（70.3534% vs 70.8996%），绝对下降 −0.546 个百分点，Bootstrap 95% 区间 [−0.964, −0.137] 与 McNemar p = 0.0112 表明下降**很小但统计上可检测**；HellaSwag 贡献主要下降（−0.71 pp，p = 0.0027），ARC-Easy 与 PIQA 无显著变化。Wiki PPL 上升 3.85%，Dolly PPL 反而下降 1.46%（作者解读为小样本上无退化证据，不能推广）。
- **融合加速**：融合分组执行较逐专家顺序 W4 参考快 **1.97×**（18.43 vs 9.36 tok/s），且 16 个贪婪 token 完全一致。

## 七、优点与亮点

1. **统一的 kernel-native 表示贯穿主机与 GPU**：缓存未命中时零反量化、零重打包，直接复制最终推断表示，极大减少 miss 路径开销，设计优雅。
2. **概念界定清晰**：严格区分“完整专家可用性”“对量化隐状态的路由忠实性”“与 BF16 的数值等价性”三个易混淆概念，明确 ExactMoE 保证前两者、不保证第三者，避免了过度声称。
3. **系统整合而非单点创新**：将专家量化、缓存管理与 MARLIN 融合内核组合为完整运行时，并且不追求数值同构，强调系统属性实证。
4. **统计严谨**：配对 Bootstrap 置信区间 + 精确 McNemar 检验 + 多任务分层报告，质量评估超越了常见的单点准确率对比。
5. **诚实的范围声明**：自述非首创新技术、不声称优于未复现的外部系统、批量扫描仅为描述性数据。

## 八、不足与局限

1. **数值不等价性**：W4A16 不保留 BF16 logits；量化改变隐状态，后续路由决策轨迹可能偏离 BF16，质量保持率因模型、任务而异。
2. **依赖主机内存与传输路径**：非驻留专家须从固定内存搬运，性能受路由局部性、缓存容量与 H2D 带宽限制；专家复用不足时吞吐收益可能消失。
3. **量化覆盖面有限**：仅路由专家被 W4 量化，注意力、路由、嵌入、共享组件、LM head 仍为 BF16，总显存节约取决于路由专家参数量占比。
4. **硬件与形状约束**：要求 MARLIN 兼容维度与分组约束，依赖 NVIDIA GPU；适配新架构需重新映射 checkpoint 张量到 gate/up/down 打包布局，移植成本不低。
5. **单机单卡限定**：不支持多 GPU 放置、分布式缓存协调与连续批处理调度器；专家权重更新需要重新打包。
6. **外推性受限**：全部结论来自单模型（OLMoE）单 GPU；未与领先的 MoE 服务系统（MoE-Infinity、Fiddler 等）在相同硬件协议下对比，批量扫描单次测量无置信区间，过程内重复不能代表跨进程波动。
7. **质量下降虽小但可检测**：聚合 12,450 题上 −0.546 pp 的下降并非完全无害，论文也承认“高保持率 ≠ 数值同一性”，未来应预先注册任务加权方案与非劣效边界。
