## 摘要
小型NLP模型，尤其是BERT家族编码器，即使在大语言模型时代，在分类、排序和检索等工业工作负载中仍然很重要。在服务器CPU上，INT8量化提供了有吸引力的延迟-吞吐量-成本权衡，但用户越来越期望这种加速能够直接在原生PyTorch栈中使用。我们将SmoothQuant集成到TorchAO中，并通过TorchInductor中的图级融合以及跨oneDNN、AVX512_VNNI和基于AMX的实现的高效INT8 GEMM内核选择，优化了英特尔至强CPU上的推理路径。在BERT、DistilBERT和XLM-RoBERTa基准测试中，该方法相对于FP32基线提供了高达5.8倍的端到端吞吐量加速，且精度损失可忽略不计，在某些情况下甚至没有可测量的损失。我们还通过使用屋顶线模型的详细性能分析验证了我们的工作。该实现已上游到PyTorch和TorchAO，使得能够使用原生PyTorch工具进行开箱即用的部署。

## Abstract
Small NLP models, especially BERT-family encoders, remain important in industrial workloads such as classification, ranking, and retrieval even in the era of large language models. On server CPUs, INT8 quantization offers an attractive latency-throughput-cost trade-off, but users increasingly expect such acceleration to be available directly in the native PyTorch stack. We integrate SmoothQuant into TorchAO and optimize the resulting inference path for Intel Xeon CPUs through graph-level fusion in TorchInductor and efficient INT8 GEMM kernel selection across oneDNN-, AVX512_VNNI-, and AMX-based implementations. Across BERT, DistilBERT, and XLM-RoBERTa benchmarks, the approach delivers up to 5.8x end-to-end throughput speedup with negligible---and in some cases no measurable---accuracy loss relative to the FP32 baseline. We also validated our work by detailed performance analysis with roofline models. The implementation has been upstreamed to PyTorch and TorchAO, enabling out-of-the-box deployment with native PyTorch tooling

## 1. 核心问题与整体含义（研究动机与背景）

- **研究背景**：尽管大语言模型（LLM）广受关注，但以 BERT 家族为代表的小型 NLP 模型在工业界的分类、排序、检索等任务中仍被广泛部署。CPU 推理因其成本优势和服务器基础设施的普及性，在这些场景中扮演着关键角色。
- **核心痛点**：在 PyTorch 生态中，直接以 FP32 精度在 CPU 上执行 Transformer 推理往往性能不佳，因为推理时间主要由矩阵乘法（GEMM）主导，存在巨大的计算和内存开销。用户期望 INT8 量化带来的加速能力能够直接在原生 PyTorch 软件栈中使用，而无需依赖第三方工具链（如 Intel Neural Compressor、ONNX Runtime、IPEX 等）。
- **硬件机遇**：现代 Intel Xeon CPU 提供了 VNNI 和 AMX 等指令集扩展，可大幅加速 INT8 GEMM 计算，这为在 CPU 上实现高效 INT8 推理提供了硬件基础。
- **核心问题**：如何在原生 PyTorch 栈中实现一套完整的、开箱即用的、高性能的 SmoothQuant INT8 推理工作流，并在不同代际的 Intel Xeon CPU 上实现接近硬件峰值的性能。

## 2. 方法论：核心思想、关键技术细节

- **总体架构**：以 TorchAO 为量化前端，以 TorchInductor 为图优化与代码生成后端，形成一条"训练后量化→图融合→内核选择→代码生成"的完整原生 PyTorch 推理链路。核心流程为：原始模型 → TorchAO SmoothQuant 量化（`torch._int_mm`）→ TorchInductor 图融合（`qlinear_pointwise`）→ CPP 后端内核选择 → 生成 C++ 代码。
- **SmoothQuant 量化方法**：通过离线校准数据计算逐通道平滑因子，将激活值中的离群值"迁移"到权重中——激活张量除以平滑因子，权重张量乘以相同因子，从而在数学等价的前提下降低激活量化的难度，使模型适合标准 INT8 量化（INT8 × INT8 → INT32 GEMM）。支持静态量化（量化参数在标定阶段固定）和动态量化（量化参数在运行时计算）两种模式。
- **TorchAO 量化流程优化**：预计算平滑因子的倒数以避免运行时重复除法；忽略不必要的张量扩展操作以避免拷贝；忽略虚拟零点以节省计算开销。
- **TorchInductor 图级融合**：针对 `torch._int_mm` 的固有局限（运行时权重布局转换开销大、缺乏 scale 和 post-operation 处理、oneDNN 元数据构造开销），设计图匹配模式 `input_reshape → int_mm → dtype_convert → mul → mul → output_reshape → add_bias`，将其融合为单个 `torch.ops.onednn.qlinear_pointwise` 算子。该算子接受块化布局权重、在核内处理激活/权重量化缩放，并在预热阶段缓存 oneDNN 元数据。权重布局转换算子通过常量折叠在编译期完成，避免运行时开销。融合后的算子还可进一步与 GeLU 等其他算子融合。
- **模板化 GEMM 内核与自动选择**：在 TorchInductor 的 CPP 后端中新增基于 AMX 和 AVX512_VNNI 指令的 INT8 GEMM 微内核，与 oneDNN 内核一起参与 TorchInductor 的内核选择机制。该机制在降级时生成候选内核，通过编译后微基准测试（micro-benchmarking）选出最快实现，从而在 oneDNN 的通用性和模板内核的形状特化之间取得平衡。
- **Ice Lake（第 3 代 Xeon）兼容方案**：针对 Ice Lake 不支持原生 s8 × s8 GEMM 指令的问题，将激活张量从有符号 INT8 移位为无符号 INT8：`Xu8 = uint8(int32(Xs8) + 128)`。利用等式 `Y = Xu8 · W^T − c`，其中补偿项 `c = (Σ_k W:,k) · 128` 可预先计算，从而以少量减法开销换取 AVX512_VNNI 的执行能力。

## 6. 主要结论与发现

- **显著性能提升**：在 Ice Lake 上，INT8 相比 FP32 实现约 1.9×~2.6× 的端到端吞吐量提升和超过 3× 的线性块延迟降低；在 Granite Rapids 上，吞吐量提升达 4.2×~5.8×，线性块延迟降低超过 7.5×。其中静态量化始终优于动态量化（因更多工作被离线预处理）。
- **INT8 相比 BF16 的优势**：在 Granite Rapids 上，INT8 相比 BF16 的吞吐量提升为 0.98×~1.59×，线性块加速为 1.45×~1.84×。DistilBERT 和 XLM-RoBERTa 出现 <1× 吞吐量提升，原因是动态量化的运行时开销超过了 GEMM 加速收益。
- **精度无损**：量化模型在 SQuAD 和 MultiNLI 上的精度损失均低于 1%，部分场景甚至与 FP32 基线持平或略高（差异可归因于评估方差，而非量化本身的系统性改进）。
- **Roofline 验证**：实际加速比与估算上限总体一致。Ice Lake（计算受限）的线性块加速比可达到理论上限的 90%~97%；Granite Rapids（内存受限）受量化/反量化开销影响更大，加速比约为上限的 78%~89%。静态量化在某些对比中（如 INT8 vs BF16 的吞吐量）实现了 104% 的上限达成率，论文解释为 roofline 模型简化假设所致。
- **工程落地**：实现已上游合入 PyTorch 和 TorchAO，用户可直接使用原生 PyTorch 工具链进行部署。

## 7. 优点

- **完全原生的 PyTorch 方案**：不需要第三方推理引擎或工具链，通过 TorchAO API 即可完成 SmoothQuant 量化，再经 torch.compile 实现图融合与内核选择，达成了"开箱即用"的部署体验。
- **全面的 CPU 代际覆盖**：同时支持 Ice Lake（AVX512_VNNI，通过 s8s8→u8s8 变换）和新一代 AMX 平台，兼顾了存量服务器和新型硬件。

- **可复现性好**：提供了详细的基准配置（CPU 亲和性、线程数、内存分配器、预热轮数等）和公开的 benchmark 代码仓库（GitHub），便于复现和后续对比。

## 8. 不足与局限

- **实验覆盖范围有限**：未与其他主流 CPU INT8 推理方案（Intel Neural Compressor、ONNX Runtime、IPEX 等）进行直接横向对比，无法直观体现该方案相对于既有工具链的优势有多大；未覆盖第 4/5 代 Xeon 平台的实测数据；未对不同 batch size、序列长度和真实生产请求模式进行敏感性分析。
- **模型范围偏窄**：评测仅覆盖三种 BERT 家族编码器模型。SmoothQuant 最初面向大语言模型设计，论文未在更大的模型（如 LLM）或更广泛的 Transformer 变体上验证该工作流，方法的通用性结论有限。
- **动态量化开销未充分优化**：动态量化在 DistilBERT 和 XLM-RoBERTa 上出现 INT8 vs BF16 吞吐量退步（0.98×、0.99×），表明量化参数搜索的运行时开销在一些场景下抵消了 GEMM 加速收益，该问题仍有优化空间。
- **roofline 模型存在简化假设**：LLC 行为假定（权重完全驻留 LLC、X/Y 数据往返主存）与真实执行可能不完全一致；线性块（GEMM + post-operations）作为 GEMM 的近似代理存在一定偏差；不同数据类型的融合行为差异（如 GeLU 在静态量化中被融合而在动态量化中未融合）使得线性块加速比并非严格的同类对比。
- **精度评估的深度有限**：精度评测仅报告了最终指标，未分析量化误差在不同层/注意力头中的分布，也未通过多次重复实验进行统计显著性检验；个别精度略高的结果被归因于"评估方差或轻微过拟合"，但缺乏数据支撑。
- **AMP 行为复杂**：自动混合精度在不同硬件上的行为差异较大（如 Ice Lake 上 BF16 转换后计算仍为 FP32，徒增开销），该机制虽然实用，但使性能分析的可控性有所下降。
