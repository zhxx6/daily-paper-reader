## 摘要
混合专家模型中，专家池远超DRAM容量的情况迫使每个服务系统都必须包含缓存，然而现有系统通常采用用户空间、基于专家粒度、频率排序、显式锁页的层次结构来实现该缓存。我们刻画了操作系统已经提供的另一种方案：将页缓存作为专家层。我们使用来自三个MoE模型的路由器追踪数据（每层128至896个专家），包括一个专家池达1.45 TB的生产级万亿参数模型，并在GH200节点上通过对完整专家池的原生重放，结合三种独立机制来强制容量限制。我们发现了四个主要结果。第一，迭代时间和设备流量是缓存容量的平滑、可复现函数，这使得DRAM成为万亿参数服务中一个实用的容量调节旋钮。第二，深度压力拐点是一个回收伪影，需要同时使用MGLRU和气球式的多数内存锁定；cgroup限制和物理内存配置没有显示这种放大效应，表明基于气球的研究可能会将压力端的设备流量高估约2倍。第三，在强制同等内存墙下，未经调优的内核LRU所服务的需求基本上与同域Oracle频率表相当（256 GB时命中率分别为75.3%和74.6%），而Oracle的机制优势仅为1.09倍，且在域外消失，此时LRU仍保持70–71%的命中率。第四，实测召回率为64.7%的路由器预读在内核预读建议下仅提供0.3%的收益，而作为同步预取则无收益。端到端来看，启用内核管理的缓存可将解码性能提升1.09–1.10倍，且在九个均衡对比组中产生令牌一致的输出。由此得出的设计原则很简单：在这种场景下，让内核负责驱逐，而将模型特定知识的最佳用途放在准入和预读建议上。

## Abstract
Mixture-of-experts models whose expert pools dwarf DRAM force every serving system to contain a cache, yet existing systems typically implement this cache in user space using expert-granular, frequency-ranked, explicitly pinned tiers. We characterize the alternative already provided by the OS: the page cache as the expert tier. We use router traces from three MoE models spanning 128 to 896 experts per layer, including a production trillion-parameter model with a 1.45 TB expert pool, and replay them natively against the full pool on GH200 nodes with capacity enforced by three independent mechanisms.   We find four main results. First, iteration time and device traffic are smooth, reproducible functions of cache capacity, making DRAM a practical sizing knob for trillion-parameter serving. Second, the deep-pressure knee is a reclaim artifact requiring both MGLRU and balloon-style mostly-mlocked memory; cgroup limits and physical-memory configurations show no such amplification, indicating that balloon-based studies can overstate pressured-end device traffic by approximately 2$\times$. Third, under an enforced equal-memory wall, untuned kernel LRU serves essentially as much demand as a same-domain oracle frequency table (75.3% versus 74.6% at 256 GB), while the oracle's mechanism advantage is only 1.09$\times$ and disappears off-domain, where LRU remains at 70--71% hit rate. Fourth, router lookahead with 64.7% measured recall provides only a 0.3% benefit as kernel readahead advice and no benefit as synchronous prefetch. End to end, enabling kernel-managed caching improves decode performance by 1.09--1.10$\times$ with token-identical outputs across nine balanced pairs. The resulting design principle is simple: in this regime, let the kernel own eviction, while model-specific knowledge is best spent on admission and advice.

## 2. 论文提出的方法论：核心思想、关键技术细节

- **核心思想**：将专家池通过 `mmap` 映射，让内核页缓存天然成为专家缓存层；驱逐（eviction）完全交给内核的 LRU/MGLRU，模型知识只用于**准入（admission）**和**预取建议（advice）**，形成 Algorithm 2 的分层设计。
- **关键方法细节**：
  - **路由轨迹捕获**：在生产引擎和 llama.cpp 中嵌入跟踪钩子，只记录 decode 阶段（排除 batched prefill 和调度器 dry-run 污染）。生产模型通过引擎的 trace hook；小模型通过 llama.cpp 的 eval-callback。
  - **规范性轨迹解析器（canonical parser）**：论文发现了推测解码（speculative decoding）造成的"一个 token"单位歧义——引擎迭代可能携带两个位置（spec-accept）或两次路由同一层（spec-fallback）。解析器从记录宽度和逐层重复重建每条记录的类型，并验证每 300 个请求 token 中恰好重建 299 个接受 token（一个被拒绝）。
  - **三种独立容量控制机制**：气球（balloon，mlock 匿名内存）、cgroup v2 MemoryMax 墙、物理 `mem=` 启动参数。论文强调"容量 C"是控制目标，与实际测量的多个量（MemAvailable、Cached、VmLck、块设备字节数、逻辑专家访问）严格区分。
  - **公平对比协议**：所有策略在相同的窗口上比较——按 60/40 划分训练窗口和测试窗口，所有策略都先在训练窗口热身再在测试窗口评分，并且用同一条规范的解析器作为所有模拟器、预测器和原生重放的共同输入。

## 6. 论文的主要结论与发现

1. **容量是可调、平滑的旋钮**：迭代时间和设备字节数是缓存容量的平滑函数（三点运行离散度 0.5–4.0%），设备读取大致服从反比容量参考（锚定 448 GB 点，偏差 +5.0% 至 -9.7%）。DRAM 成为可量化的服务调优手段。
2. **深度压力拐点是回收伪影——且气球位于其中**：C≈64 GB 时设备流量 33.6 GB/迭代，超过名义未命中需求的两倍多。该放大需要同时具备 MGLRU 和气球式"大部分 mlock"内存形态（81% 锁定失败、74% 不失败）；cgroup 墙和物理 `mem=` 启动在任何测试容量下都不放大。基于气球的容量研究在默认内核上可将压力端设备流量高估约 2 倍（一处 2.0x，另一处 2.6x）。
3. **最近性（recency）在主机层预算下是正确的策略**：在公平窗口下，朴素 LRU 命中率达到 75.3%，与同域 oracle 频率表的 74.6% 持平；在每层预算大于约 2k 专家时 LRU 全面胜出，小缓存下频率策略反超。全局池与逐层模拟一致（偏差 2.7 pp 内）。
4. **所有者机制的真实代价是个位数**：在强制等内存墙下，oracle 固定（pinned）竞技场相对于页缓存的机制优势仅为 1.09x（C=256 GB；128 GB 时为 1.11x），设备流量几乎相同（7.4 vs 7.2 GB/迭代），差距来自内核的查找和回收开销而非所选字节更优。禁用读预取（FADV_RANDOM）让页缓存更慢（1.80 s）。
5. **域外**：用散文训练的 oracle 固定表服务其他域时命中率降至 21–34%，而无表 LRU 在所有域保持 70–71%。
6. **预取**：真实 PILOT 预测器以 64.7% 召回率提供 fadvise 建议仅带来 0.3% 收益（oracle 上限为 5.0%）；相同 hint 以同步 pread 执行则无收益。Belady 显示仍约有 1/4 的未命中理论上是建议可寻址的。
7. **端到端**：在生产引擎中，打开缓存准入带来 5.3x 的机制上限提升（13.1 → 68.9 GB/s），端到端解码提速 1.09–1.10x，九个平衡对全部 token 一致（SHA-256 相等）。
8. **多级拥有权计算**：到 DRAM 的准入是免费的（未命中已经付出了 NVMe 读取）；在相干链路上 HBM 拥有权在 k*=1.06 次重用后回本；adopt 与 streaming 相差在 5.6% 以内。

  - 回收归因仅覆盖两台机器、一个内核系列（6.8）、每台一个 NVMe 类别；论文明确承认这是行为定位而非机制级证明（generation-counter 审计留给未来的内存管理社区工作）。
  - 生产模型轨迹是 242–290 引擎迭代（299 接受 token）每域，四个提示族代表领域；4,000 步渐近线来自 128 专家模型而非生产模型。
  - 无法在 480 GB 主机上将 18.6 GB 开放模型强制进入页缓存流式模式（-cpu-moe 使用匿名内存、全量卸载可入 HBM），因此 2% 的 Apple-silicon mmap 平价结果来自早期活动。
  - 未覆盖多节点推理、prune-vs-cache 的质量维度、到达过程、采样解码（论文承认采样会使热集漂移更快，但这是强化 recency 结论的方向而非削弱）。
  - 批处理合并（batch-4）省略了到达过程模型。
- **偏差风险**：
  - 端到端 A/B 是演示级重复（每组 3 对）而非统计分布，报告中位数带范围而非置信区间。
  - MGLRU-off 在气球下跨重复发散 38%，"off"是近名义值而非无噪声。
  - 不同机器的设备速度差异达 3 倍，某些单元格的比较混杂了机器差异与机制差异（论文承认并在解读时注意）。
  - 频率表 oracle 对 pinning 有利，但即使在最有利条件下 pinning 依然只赢 1.09x。
- **应用限制**：
  - 结论基于 GH200 这类具备相干链路的硬件；在 PCIe 机器上 adopt 行消失，"own-or-restream"才是用户态 HBM 缓存真正有价值的场所。
  - Darwin 无法安全到达深度压力区，因此 §5 的结论严格限于 Linux。
  - 预取结论仅在 64.7% 召回率的特定预测器上验证，逐层召回率范围 1–84% 意味着均匀预取深度可能浪费预算在难以预测的层上。
  - 论文只给出了一个时间点的容量响应（4 点、1 个轨迹、1 个宿主），明确声明这不是定律，但足以支撑工程化容量规划。
